     Context

     Audio-only mode (the default path) often lands on the wrong frame for
     YouTube videos because:
     1. Whisper returns segment-level timestamps (5-30s windows), and
     pipeline.py blindly uses the segment start as the extraction point — can be
     15s before the phrase is actually spoken.
     2. YouTube auto-generated captions (word-timestamped VTT) exist for almost
     every YouTube video but are never downloaded or used.
     3. extract_frame_at truncates instead of rounding the frame seek.

     These three issues compound: even a precise audio timestamp gets the wrong
     frame due to truncation, and imprecise timestamps get the wrong scene
     entirely.

     ---

     Root Causes (ranked by impact)

     1. Audio-only mode uses segment start, not phrase position

     pipeline.py:65: t = priority[0][0] — segment start can be 5-30s before the
     phrase.
     prior.py:128: word_timestamps=False — Whisper returns whole segments, no
     per-word timing.

     Fix (two parts):
     - Enable word_timestamps=True in audio_prior. Store words in the cache. Do
     a sliding-window phrase match over the word list to find the precise moment
     the phrase begins → return tight (word_start - 0.2, word_end + 0.5)
     windows.
     - Cache format: rename cache to audio.transcript.<model>.json (e.g.
     audio.transcript.small.json) so changing the model (or old segment-only
     caches) don't interfere. _transcript_cache(audio_path, model) takes model
     name.

     2. YouTube VTT captions not downloaded or used

     ingest.py:45: yt-dlp opts have no writeautomaticsub. The info dict has
     automatic_captions keys but no files are saved.

     Fix:
     - Add writeautomaticsub=True, subtitleslangs=["en","en-US","en-GB"], 
     subtitlesformat="vtt" to yt-dlp opts in _download_and_meta. Files land as
     video.en.vtt etc.
     - Add vtt_paths: list[Path] to VideoInfo. On cache hit (line 37-39), glob
     for existing *.vtt files instead of returning [].
     - In prior.py, add vtt_prior(vtt_path, target) → list[tuple[float,float]]:
       - Parse YouTube VTT: each cue's body contains <HH:MM:SS.mmm><c> word</c>
     tags. Strip HTML tags to get plain text per cue; also extract the inline
     word timestamps.
       - Slide a word window over the sequence; fuzzy-match joined word windows
     against target.
       - Return tight (word_start - 0.1, phrase_end + 0.3) windows.
     - In pipeline.py, check vtt_prior first (before subtitle_prior and
     audio_prior) — VTT is the most precise and cheapest prior.

     3. extract_frame_at truncates frame number

     scan.py:39: int(t * fps) — always rounds down. At 30fps, a 0.5-frame error
     = 17ms off, stacking with already-imprecise timestamps.

     Fix: round(t * fps).

     4. Whisper "base" model has high WER

     prior.py:127: WhisperModel("base", ...). Base is fastest but least
     accurate; wrong words → missed phrase matches.

     Fix: Add --whisper-model CLI arg to pipeline.py (default "small"). Thread
     it into audio_prior(audio_path, target, model="small", ...). Cache key
     includes model name so switching models doesn't reuse stale transcripts.

     5. _fine_scan fallback returns FOUND without score check (minor)

     scan.py:157-164: when fine scan finds nothing before rough_t, it re-reads
     rough_t and returns ScanResult(status="FOUND") regardless of the re-read
     OCR score.

     Fix: compute score = fuzz.WRatio(...) on the fallback; only return FOUND if
     score >= FUZZY_THRESHOLD, else return NOT_FOUND (the coarse hit was likely
     a false positive).

     VTT Format Reference

     YouTube VTT cue body looks like:
     <c.colorCCCCCC><00:00:05.120><c> My</c><00:00:05.520><c>
     mind</c><00:00:05.920><c> rebels</c></c>
     Parse with regex: r'<(\d{2}:\d{2}:\d{2}\.\d{3})><c>\s*([^<]+)</c>' →
     (timestamp, word) pairs. The cue header timestamp is the window start
     fallback.

● Here's a breakdown of all viable approaches, from simplest to most involved:

  ---

  Root cause

  Your IP hit YouTube's rate limit (HTTP 429) from the repeated failed download
  attempts. YouTube then requires bot verification, which yt-dlp can't pass
  without a real browser session. The Chrome impersonation (ImpersonateTarget)
  handles the User-Agent but not YouTube's proof-of-origin check.

  ---

  Approach 1: Pass browser cookies (easiest, most reliable)

  Export your logged-in YouTube session cookies directly from Chrome/Firefox.
  yt-dlp supports this as a Python API option:

  "cookiesfrombrowser": ("chrome",),   # or ("firefox",) / ("chromium",)

  Added to _YDL_OPTS in ingest.py, this tells yt-dlp to read your browser's
  cookie store and pass the session to YouTube. Because you're already signed
  into YouTube in Chrome, the request looks like a real user.

  Limitation: Only works on the machine where the browser is installed. Won't
  work in headless/server environments.

  ---

  Approach 2: Switch player client to tv or android

  YouTube runs multiple internal clients (web, android, iOS, TV, etc.). The TV
  client (TVHTML5) is the least scrutinised — it gets fewer bot challenges
  because it can't run JavaScript challenges in a set-top box. In yt-dlp Python
  API:

  "extractor_args": {"youtube": {"player_client": ["tv"]}},

  Or android as an alternative. These clients don't require a PO token.
  Downside: may return fewer available formats/resolutions.

  ---

  Approach 3: PO Token (Proof-of-Origin)

  Since 2024 YouTube requires a proof-of-origin token for the web client — a
  value generated by YouTube's own JavaScript in a real browser tab. yt-dlp
  can't generate one itself; you extract it manually using a browser extension
  (youtube-po-token-generator) or a Node.js script.

  "extractor_args": {
      "youtube": {
          "player_client": ["web"],
          "po_token": ["web+<TOKEN_VALUE>"]
      }
  }

  Most reliable for server/headless use, but requires manual token renewal
  (tokens expire after hours/days).

  ---

  Approach 4: Rate-limit the requests

  The 429 was triggered by rapid retries. Adding sleep between requests reduces
  the chance of being flagged:

  "sleep_interval_requests": 2,
  "sleep_interval": 3,

  This doesn't fix bot detection but reduces the rate-limit risk.

  ---

  Approach 5: Update yt-dlp

  Outdated yt-dlp versions trigger detection more often because YouTube's client
  fingerprints change frequently:

  pip install -U yt-dlp

  ---

  Recommended combination for this project
